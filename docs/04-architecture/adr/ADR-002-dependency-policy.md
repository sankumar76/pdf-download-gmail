# ADR-002: Runtime dependency policy, time-zone data (Q-08) and no YAML

| Field | Value |
|-------|-------|
| Status | Accepted |
| Date | 2026-10-29 |
| Deciders | solution-architect |
| Related | NFR-014, NFR-020, NFR-023, FR-008, CONSTRAINT-03, D-04 (CFG-11 Won't), Q-08, coding-standards §5, §11, ADR-001 |

## Context
The RD allows only the Google client libraries "unless justified". NFR-023 requires an accepted ADR for every other runtime dependency. Two needs exist beyond Google's libraries: (1) the GUI toolkit (ADR-001); (2) time zones. `zoneinfo` (stdlib) needs an IANA database; Windows has none, so `zoneinfo.ZoneInfo("Asia/Kolkata")` fails without the `tzdata` package. FR-008 also needs the **system** zone as an IANA name (shown and editable in the GUI); Windows reports a Windows zone name ("India Standard Time"), and the stdlib has no Windows→IANA mapping. The settings-file feature (CFG-11) that would need a YAML parser is a Won't (D-04).

## Decision Drivers
- NFR-023 (0 unapproved deps), NFR-014 (no egress, no telemetry), TB-5 supply-chain risk
- Correct DST-aware dates on Windows (FR-008, FR-022)
- Licence compatibility; maintenance health

## Considered Options
### Option A — Allow-list with `tzdata` + `tzlocal` (chosen)
- Pros: `tzdata` is the PSF-maintained IANA data package that `zoneinfo` falls back to automatically (Apache-2.0, data only, no code paths). `tzlocal` returns the system IANA name on every OS, mapping Windows zones via CLDR data (MIT, small, widely used).
- Cons: two more packages to pin and audit; `tzdata` must be refreshed when IANA publishes changes.
### Option B — `tzdata` only + vendored CLDR `windowsZones` mapping
- Pros: one fewer package.
- Cons: we own a data file and its updates; reimplements what `tzlocal` does; more code to test.
### Option C — fixed UTC offset from `datetime.now().astimezone()`
- Pros: no dependency.
- Cons: wrong across DST changes inside a range; cannot show an IANA name; fails FR-008. Rejected.

## Decision
**Runtime allow-list (exhaustive):** `google-api-python-client`, `google-auth`, `google-auth-oauthlib`, `google-auth-httplib2` (and their transitive dependencies), `tzdata`, `tzlocal`, `PySide6-Essentials` (ADR-001; imported only by `gmail_pdf.gui`). No YAML parser and no `python-dotenv` (D-04). **Dev/CI-only:** pytest, pytest-cov, pytest-qt, diff-cover, ruff, mypy, pip-audit, bandit, pip-tools; gitleaks runs as a CI action/binary.

Rules:
1. Versions are pinned exactly with hashes in `requirements.txt` (runtime) and `requirements-dev.txt` (includes runtime), generated by `pip-compile --generate-hashes` from `pyproject.toml`; installs use `--require-hashes`.
2. A new runtime dependency needs a new ADR (or an amendment here) with licence and `pip-audit` result; CI fails if an installed top-level runtime package is not in the allow-list (`tests/unit/test_dependency_allowlist.py` reads `pyproject.toml`).
3. Licence allow-list: Apache-2.0, MIT, BSD, PSF, MPL-2.0, LGPL-3.0 (dynamic linking only). GPL-only packages are not allowed.
4. `pip-audit` (PR gate) — a known vulnerability with a fix blocks the PR; without a fix, master decides and a `tech-debt` issue records it.
5. Time zones: resolve with `tzlocal.get_localzone_name()`; construct with `zoneinfo.ZoneInfo`; list with `zoneinfo.available_timezones()`. `tzdata` is a hard dependency on every OS so tests behave the same everywhere.

## Consequences
- Positive: Windows dates are correct across DST; the dependency surface is explicit and machine-checked.
- Negative: periodic `tzdata` bumps (handled by normal dependency updates); two extra audit targets.
- Follow-up: developer creates `pyproject.toml`, pinned requirement files and the allow-list test in the first W1 story; first `pip-audit` result is an AC of that story (no CVE scan was run at G3).

## Verification
Allow-list test in CI; `pip-audit` on every PR; boundary tests for FR-008 under `Asia/Kolkata`, `America/New_York` (DST crossing) and `Pacific/Kiritimati` on the Windows CI runner.
